Правильный ответ зависит от бизнес-логики ваших подписок, а точнее — от того, зависит ли состояние одной подписки от другой, и насколько «тяжелая» обработка внутри них.
В реальном мире для Caplin DataSource используют баланс: один SerializingExecutor на логическую сессию клиента (одно соединение StreamLink).
Ниже разберем, почему сотня экзекуторов — это избыточно, когда один экзекутор начнет тормозить, и как найти золотую середину.

Модель 1: Один SerializingExecutor на ВСЕГО клиента (Рекомендуется по умолчанию)

Вы создаете один экзекутор на одно физическое соединение StreamLink (на уровне Peer в Caplin DataSource API). Все 100 подписок этого клиента обрабатываются последовательно друг за другом в одной очереди сессии.

Плюсы:

• Идеально для реактивного стриминга (Backpressure): Вы можете централизованно контролировать поток данных к конкретному клиенту. Если у клиента «узкий» интернет-канал, вы тормозите всю его сессию целиком.
• Минимум оверхеда: На 1000 активных клиентов у вас будет ровно 1000 экзекуторов. Память не расходуется впустую.

Будет ли тормозить?

Нет, в 95% случаев тормозить не будет, если вы соблюдаете главное правило RPC-архитектуры: код внутри SerializingExecutor должен быть строго неблокирующим (Non-blocking I/O).
• Если обработка сообщения — это просто парсинг тегов, обновление мутабельного стейта в памяти и вызов dataSource.sendRecord(), то один поток процессора может переваривать сотни тысяч таких операций в секунду. Сотня подписок одного клиента для него — секундная пыль.
• Когда начнется торможение: Если внутри обработчика подписки №1 вы случайно сделаете блокирующий вызов (например, синхронный запрос в базу данных или Thread.sleep()), то подписки со 2-й по 100-ю встанут в очередь и будут ждать.

Модель 2: Один SerializingExecutor на каждую подписку (На каждый Subject)

Вы создаете отдельный экзекутор на каждый Subject (например, один для /FX/EURUSD, один для /FX/GBPUSD и т.д.).

Когда это нужно?

Только в одном случае: если обработка каждой подписки изолирована, требует тяжелых CPU-вычислений (например, сложный realtime-магический расчет деривативов на лету), и вы хотите, чтобы подписка на EURUSD считалась на Core 1 процессора, а GBPUSD — параллельно на Core 2 для одного и того же клиента.

Минусы:

• Взрывной рост объектов: Если 1000 клиентов подпишутся на 100 инструментов каждый, у вас в памяти будет 100,000 экзекуторов и 100,000 очередей. Это убьет кэш процессора из-за постоянного переключения контекста (Thread-Hopping), и система начнет тормозить целиком, а не для одного клиента.

Как спроектировать правильно? (Архитектурный консенсус)

Для систем типа Caplin (маркет-дата, трейдинг) лучшим решением является привязка SerializingExecutor к бизнес-контексту (сессии клиента), но с разделением на уровне глобальных пулов:
1. Создавайте один SerializingExecutor на сессию клиента (Peer в Caplin). Это гарантирует, что StreamLink получает данные в правильном порядке, а вы не плодите тысячи очередей.
2. Обеспечьте асинхронность: Если подписке нужно сходить в БД или в тяжелый микросервис, этот «поход» должен выполняться на стороннем пуле (например, CompletableFuture или реактивный Mono.fromCallable()). Как только данные из БД пришли, результат возвращается обратно в SerializingExecutor клиента для безопасной отправки ответа.
java
// Пример правильного проброса тяжелой задачи
public void handleHeavyRequest(GenericMessage msg) {
    // Мы в потоке клиента. Не блокируем его!
    databasePool.execute(() -> {
        var result = db.fetchData(msg); // Тяжелый блокирующий I/O
        
        // Возвращаем результат в экзекутор клиента для отправки ответа
        clientSessionExecutor.execute(() -> {
            dataSource.sendResponse(result); 
        });
    });
}
Используйте код с осторожностью.
Если у вас в подписках планируются тяжелые CPU-вычисления или блокирующие вызовы (БД, сторонние API), напишите об этом. Я покажу, как правильно вынести их из SerializingExecutor сессии, чтобы они не подвешивали обработку остальных подписок клиента.
