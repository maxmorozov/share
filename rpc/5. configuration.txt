Учитывая, что ваша RPC-библиотека будет обслуживать кардинально разные бизнес-сценарии — от высокочастотных котировок (FX подписки) с ультра-низкой задержкой до тяжелых аналитических батч-запросов (KDB+/исторические базы данных), — жестко зашивать одну модель пулов и экзекуторов в код библиотеки нельзя.
Архитектурно правильное решение — спроектировать конфигурируемую фабрику контекстов исполнения (Execution Context Factory). Пользователь библиотеки (разработчик конкретного сервиса) должен иметь возможность одной строчкой в коде или конфиге переключать поведение вашей библиотеки под свою специфику.
Ниже представлена готовая схема интерфейсов и конфигурации для вашей RPC-библиотеки.

1. Архитектурный интерфейс конфигурации

Для начала введем понятие RpcExecutionContext, который инкапсулирует в себе способ упорядочивания задач (Executor) и стратегию пулинга объектов (TaskPool).
java
import java.util.concurrent.Executor;

/**
 * Контекст выполнения для конкретного RPC-сервиса или сессии.
 */
public interface RpcExecutionContext {
    
    /**
     * Возвращает экзекутор для обработки входящих REQUEST/вызовов.
     */
    Executor getExecutor();

    /**
     * Арендует задачу из пула под данный контекст (Zero-Allocation паттерн).
     */
    PooledRpcTask borrowTask();

    /**
     * Освобождает ресурсы по окончании жизненного цикла контекста (например, при отписке).
     */
    void close();
}
Используйте код с осторожностью.

2. Реализация профилей под разные задачи

Пользователю библиотеки мы предлагаем три готовых преднастроенных профиля (Режима выполнения).

Профиль А: "REALTIME_FX" (Low-Latency, High-Frequency)

• Для чего: Стриминг валютных котировок, стаканов.
• Как устроен под капотом: Один SerializingExecutor на сессию клиента, работающий поверх фиксированного пула потоков (Fixed CPU Thread Pool). Очередь на базе MpscArrayQueue (JCTools), пул задач на базе Netty Recycler или StripedPool.
• Поведение: Если очередь клиента забивается, применяется жесткий Backpressure или сброс старых котировок.

Профиль Б: "ANALYTICS_KDB" (I/O & CPU Intensive, Batching)

• Для чего: Запросы исторических данных из KDB+, тяжелые SQL/NoSQL выборки.
• Как устроен под капотом: Отдельный Executor на базе виртуальных потоков Java 21+ (Executors.newVirtualThreadPerTaskExecutor()). Поскольку KDB или диск могут заблокировать поток на сотни миллисекунд, виртуальные потоки не дадут серверу задохнуться.
• Поведение: Пулинг объектов RpcTask здесь практически не нужен (или используется стандартный слабый пул), так как на фоне тяжелого запроса к KDB микро-аллокация одной лямбды не создаст заметного оверхеда. Потокобезопасность обеспечивается тем, что под каждый запрос выделяется свой независимый виртуальный поток.

3. Конфигурирование через Fluent API (Реализация в библиотеке)

Позвольте разработчикам настраивать RPC-методы при регистрации сервиса в вашей библиотеке:
java
// Пример того, как конечный разработчик будет настраивать ваш RPC-сервер
RpcServer rpcServer = RpcServerBuilder.create(port)
    
    // Сервис котировок настраиваем на ультра-реалтайм
    .registerService(new FxMarketDataService(), RpcConfig.builder()
        .setProfile(ExecutionProfile.REALTIME_FX)
        .setQueueCapacity(2048)
        .setPoolingEnabled(true)
        .build())
        
    // Сервис отчетов KDB настраиваем на тяжелый параллельный I/O
    .registerService(new KdbHistoryService(), RpcConfig.builder()
        .setProfile(ExecutionProfile.ANALYTICS_KDB)
        .setMaxConcurrentRequests(50) // Ограничиваем лавину запросов к KDB
        .build())
        
    .build();
Используйте код с осторожностью.

4. Внутренняя оркестрация в диспетчере вашей библиотеки

Внутри сетевого адаптера Caplin DataSource (или любого другого транспорта) вы выбираете нужный контекст выполнения на основе метаданных метода:
java
public class RpcMessageDispatcher {
    
    private final Map<String, RpcServiceMetadata> registry = new ConcurrentHashMap<>();

    // Вызывается IO-потоком транспорта (например, Caplin)
    public void dispatch(Peer peer, GenericMessage message) {
        String serviceName = message.getField("SERVICE_NAME");
        RpcServiceMetadata service = registry.get(serviceName);
        
        if (service == null) {
            sendError(peer, message, "Service not found");
            return;
        }

        // Получаем контекст выполнения, выделенный под этот сервис/клиента
        RpcExecutionContext context = service.getExecutionContextFor(peer, message);
        
        // 1. Арендуем задачу из пула, специфичного для этого профиля
        PooledRpcTask task = context.borrowTask();
        
        // 2. Инициализируем мутабельные данные без аллокаций
        task.init(message, service.getHandler());
        
        // 3. Отправляем в экзекутор (это может быть как SerializingExecutor для FX, 
        // так и Virtual Thread Executor для KDB)
        context.getExecutor().execute(task);
    }
}
Используйте код с осторожностью.

Резюме архитектурного подхода

Предоставив разработчикам абстракцию ExecutionProfile, вы делаете библиотеку универсальной:
1. Для валютных пар (FX): Библиотека включает lock-free очереди, Netty Recycler и SerializingExecutor на сессию, выдавая максимальный throughput и microsecond-задержки.
2. Для KDB: Библиотека отключает сложный пулинг, убирает последовательную сериализацию (так как запросы KDB независимы) и разворачивает под каждый запрос виртуальный поток, позволяя выполнять сотни тяжелых аналитических выборок параллельно.
